## 설계 결정

### 쿠키 인증과 CSRF

- 로그인/회원가입 성공 시 access/refresh token을 별도 HttpOnly 쿠키에 저장하며 응답 JSON에 토큰을 노출하지 않는다.
- 로컬은 `SameSite=Lax`, `Secure=false`; 운영용 Secure 값은 환경변수로 둔다. 프런트는 `credentials: "include"`를 사용한다.
- `POST /auth/refresh`, `POST /auth/logout`을 추가한다. 상태 변경 POST/PUT/DELETE는 double-submit CSRF 쿠키와 `X-CSRF-Token` 일치를 요구한다.
- CORS는 `http://localhost:5173`만 credentials와 함께 허용한다.

### 데이터

- 게스트 서명 키는 새 서버 환경변수로 관리하고 `.env.example`에 이름만 기록한다.
- 게스트 방도 기존 테이블을 사용하되 회원/게스트 소유자를 구분할 새 migration을 추가한다. 타 사용자/게스트 방은 404다.
- `user_profiles`에는 `name`, `age`, `learning_goal_other`를 새 migration으로 추가한다. 이메일 원본은 Supabase Auth이며 중복 저장하지 않는다.
- 기존 migration은 수정하지 않으며 공용 DB에 DROP/TRUNCATE를 실행하지 않는다.

  - **Verify:**     `npm run test -- --run src/api/runtime-fixture-boundary.test.ts`
  - **Breaker:**    `web/src/api/client.ts` :: `import type` -> `import * as fixtures`
  - **Expect-red:** AC-T14-FIXTURE-BOUNDARY
  - **Observed:**   미관찰
  - **Negative:** 문서/생성물에 실제 키·토큰·서명 secret을 넣지 않는다.
